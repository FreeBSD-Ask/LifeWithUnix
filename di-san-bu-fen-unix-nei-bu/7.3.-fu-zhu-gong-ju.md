# 7.3 辅助工具

UNIX 为程序员提供了种类繁多、功能强大的工具，辅助编程工作。有些工具本身相当复杂，掌握它们花的时间不亚于学一门编程语言。Jon Bentley 在《Communications of the ACM》的“Programming Pearls”专栏里，就把 yacc、lex 这类工具称作“小语言”，因为它们从结构上看就像一门通用编程语言，连解析器都有。

不管多难学，它们总能省下开发和调试的时间。我们离了它们就没法活。

幸运的是，几乎所有如今已成经典的 UNIX 工具都迁移到了非 UNIX 环境。The Virtual Operating System（虚拟操作系统）最早把其中大多数带给非 UNIX 机器；如今，只要机器有 C 编译器，几乎都能弄到这些工具。许多系统厂商也把它们作为系统的必备部分提供。

## 7.3.1 调试器

> “修不好，就说明它没坏。”——Walt Weir 中校

调试器用来检查运行中（原文如此）的程序有没有 bug。每个系统都有自己的调试器，UNIX 也不例外。不过，UNIX 调试器的质量历来低于其他 UNIX 工具的水平。

早期 UNIX 带有原始的汇编调试器 db 和原始的 C 调试器 cdb。第 7 版用更友好的 adb 取而代之，它同时懂汇编和 C。大多数 UNIX 版本至今仍提供 adb，只是如今它被认为只适合给二进制文件打补丁。不幸的是，每台机器上的 adb 都略有不同——这也可以理解，因为汇编器和机器本身因系统而异。

C 编译器接口也是如此。不过，有几款调试器流行了起来。伯克利的发行版引入了 sdb（符号调试器，adb 的改进版）和用户界面友好的 dbx。两者都是源码级调试器，也就是说，调试器能显示正在执行的是哪一行 C 代码。另一款极受欢迎的调试器是自由软件基金会的 gdb（GNU 调试器）。

讽刺的是，与微机上的调试环境相比，大多数 UNIX 调试器至今仍相当原始。部分问题在于 UNIX 环境本身妨碍调试：UNIX 对“从一个进程控制另一个进程”支持得很有限，而这正是调试器需要做的事。把另一个进程的内存映射进调试器进程，基本上不可能。调试器的实现只好玩各种花招来绕过这些限制。

超越所有这些调试器的一条路，是使用 C 解释器。这类解释器内嵌了更多编译器功能，因此可以在很高的层次上与调试器/解释器交互。销售 C 解释器的公司见讲应用的章节。

## 7.3.2 make

> “系统的结构反映了构建它的组织的结构。”——Richard E. Fairley

make（由 Stu Feldman 编写）是一个工具，用来拿一组源文件管理编译过程，生成可执行程序。make 依据（存放在 makefile 里的）“依赖关系”控制程序编译和链接的顺序。有了这些依赖关系，make 能判断哪些源文件需要重新编译、哪些不需要，省下大量时间和脑力。

比如，你可以告诉 make：十个 C 源文件里有五个依赖某个特定的包含文件。一旦你改动了那个包含文件，就可以放心，make 会只重新编译那五个依赖它的 C 源文件，别的都不动。

make 有许多内建规则。比如，它知道如果你改了 foo.c，就必须先重新编译 foo.c，然后才能把 foo.o 链接进程序。但它完全是通用的：只要文件之间的依赖关系可按时间顺序关联，make 就能用来跟踪任何一组文件。比如，你在给客户做支持、对产品做了改动，可以轻松让 make 生成的介质只包含自客户上次收到更新以来发生变化的那些文件。

除了最琐碎的程序，make 对一切都有用，而且能优雅地扩展到大型程序。事实上，整个 UNIX 系统就是由一组 makefile 描述的，make 能据此从源码重建整个系统。如果没有 make，要决定用 cc、ld、as、yacc、lex、mv、cp、sed 和 ln 重建一套复杂软件时该走哪些步骤，那将是一场噩梦。

make 的用处再怎么强调都不为过。有了编辑器和一门语言，程序员下一个该掌握的工具就是 make。事实上，它正是被移植到其他所有计算机系统的 UNIX 工具之一，连公有领域都有它的版本。没有任何借口不装不用 make。

## 7.3.3 版本控制

> “做好扔掉一个版本的打算——反正你总会扔的。”——Fred Brooks
>
> “如果你打算扔掉一个，你会扔掉两个。”——Craig Zerouni

版本控制让几个人能同时处理一组文件而不踩到彼此的脚，也让人能以可管理的方式发布产品的各个版本。

SCCS（Source Code Control System，源码控制系统）最初随 PWB UNIX 分发，如今是 System V 和伯克利 UNIX 的必备部分。SCCS 由 Marc Rochkind 编写。RCS（Revision Control System，修订控制系统）由 Walter Tichy 编写，意在改进 SCCS 的一些特性。RCS 不属于公有领域，但只要联系作者，就可以随商业产品免费分发。

RCS 和 SCCS 都提供受控的文件访问，用于版本控制。这解决了 UNIX 缺少高层文件锁的问题（现实世界一章有讨论）。一组源码可以用一个版本号来指代。

对文件的访问由自动化的源码管理员控制。比如，这套管理软件允许任意时刻只有一个人以写方式编辑某个文件，而任意多的人可以以其他方式使用它。管理员记录所有更新，因此只要发一条命令、指明想要的版本，就能回到某套软件的早期版本。系统自动维护历史记录，让你能追溯每次改动的原因。

这类系统的主要用途是源码控制，但它们都足够通用，能管理任何类型的文件。比如，两位合写一本书的作者，可以用其中一套系统来避免互相覆盖对方的修改。

大多数版本控制系统的灵活性远超我们这里的说明。有一个要点：RCS、SCCS 这类系统跟踪的是**改动**，而不是把每个版本完整保存一份。这比保存每个版本的完整副本更费时间，却更省空间。当旧版本很少被查阅时——维护软件时通常如此——这种方案正合适。

有些别的操作系统直接在文件系统里支持文件版本，通常是把文件名的一部分当作版本号。比如，DEC 的 VMS 文件系统通过给文件名附加版本号来保存多个版本。UNIX 若有这种版本机制固然好，可它解决不了 RCS、SCCS 所解决的长期代码控制问题。而且，内建版本机制会把你限制在文件系统设计者最初提供的能力范围内；代码控制系统则是用户级程序——可以按需扩展、修改，甚至替换。

## 7.3.4 yacc 与 lex

> “一个人的数据，就是另一个人的程序。”——Guy Steele, Jr.

yacc（yet another compiler compiler，又一个编译器编译器）和 lex（lexical analyzer，词法分析器）是帮助创建新语言的两件强大工具。它们常一起使用，但并非必须。

lex 是词法分析器——这是扫描器或分词器的花哨叫法。它读取输入流，把它拆成一个个记号（token）。记号由你定义：比如，很容易教 lex 识别字面量、数字和运算符。扫描任何编程语言，大部分工作就是这些。

把语言规格交给 lex，它就会把规格转换成一段 C 例程，你把它作为编译器的前端插进去。lex 能做的可不只是扫描输入里的数字和单词：它其实是一个正则表达式模式匹配器。只要你能用正则表达式描述模式（一种超出本书范围的理论分类），lex 就能识别。lex 允许你指定“动作”，也就是识别到某物时执行任意 C 过程。这已经强大到往往单靠 lex 就能写出整门语言。

yacc 与 lex 很像，也识别模式，也可以给每个模式关联动作（C 过程）。但 yacc 识别的模式集合比 lex 大得多：这些模式定义了 LALR(1) 文法类，强大到足以描述几乎所有现存编程语言。yacc 还不足以描述英语这类自然语言。

这些定义是高层描述。比如，yacc 文法里描述 C 的 do 语句的模式是：

```
do-statement : do statement while ( expression ) ;
```

其中 statement 和 expression 在文法别处描述，关键字和标点则作为记号被识别（也许由 lex 完成）。动作没有显示出来。yacc 使用的文法与 BNF 非常相似——BNF 是计算机科学家用来描述上下文无关语言的理论语言。

由于 UNIX 系统自带的 yacc、lex 文档少得可怜，对于打算大量使用 UNIX 编译器工具的人，我们强烈推荐 Schreiner 与 Friedman, Jr. 的《Introduction to Compiler Construction with UNIX》。比如，书中包含一个对 yacc 的修改（即便你只有二进制 UNIX 许可也能用），能大幅改进 yacc 所建解析器给出的错误信息。当然，这本书替代不了一本好的编译原理教材。

和 lex 一样，yacc 除了编译器还适用于许多类型的问题。比如，yacc 使用自己独特的一套输入语言，但它本身不是编译器。自然，yacc 就是用 yacc 定义的！

yacc 由 Steve Johnson 编写，lex 由 Mike Lesk 编写。如今有许多改进版的 yacc 和 lex，包括若干公有领域的版本——比如 GNU 项目就各有一个免费版本。

这些工具在早期 UNIX 中的可用性，大大降低了为 UNIX 构建语言的工作量。即便在今天，如果你要自己写一个 C 编译器，从一份 C 的 yacc 描述入手也是明智的。Kernighan 与 Ritchie 的《The C Programming Language》第二版附录里就有一份。

## 7.3.5 性能剖析

> “最快的算法，常常可以换成一个几乎一样快、却好懂得多的算法。”——Douglas Jones

在 UNIX 上，程序调优叫**性能剖析**（profiling）。对程序做剖析就是做一次运行时分析，然后你就能知道代码各部分花了多少时间，子程序被调用了多少次。想让程序跑得更快时，这些信息特别有用。

剖析由系统调用 profil() 和库例程 monitor() 支持，但程序员不必直接跟它们打交道。大多数语言只要提出要求就会自动生成剖析代码——比如，`-p` 选项会让 C 编译器在每次子程序调用前后插入特殊代码，链接器也会使用带剖析的库。

程序运行时会产生一个叫 **mon.out** 的文件，里面是剖析得到的原始数据。随后，可以在 System V 上用 prof、在伯克利系统上用 gprof 来解释这个原始数据文件。prof 能生成数据的图形化显示；gprof 会生成调用图，显示子程序调用的链条。System V 还有 lcomp，能产生逐行的程序剖析。

## 7.3.6 lint

> “细节决定成败。”——Peter Weinberger

早期的 C 编译器不做多少错误检查。实现者认定编译器只需对合理的程序做出合理的事，于是发现编译器写起来容易多了。

不幸的是，错误程序能否被检测出来就没有保证了。有 bug 的程序常常一声不响地编译通过，产出同样毫无意义的结果。比如，C 编译器会让你不带参数调用 sqrt()，然后干脆对本该放参数的地方——堆栈上某个随机垃圾——开平方。

这是一个本可在编译期发现、却要等到运行期的明显问题的例子。lint 是一个对 C 程序极其挑剔的程序（名字由此而来）：它能发现我们刚才讨论的问题，以及大多数其他编译期问题。它不纠正这些问题，但会提醒你许多潜在 bug。lint 的类型检查比 C 编译器严格得多，会指出那些编译得过、却可能出错的类型不匹配赋值，比如不同数据类型的指针赋值；它还会警告未使用变量、参数用法不一致之类的问题。

你也可以通过在程序里写注释来与 lint 交流。比如，要告诉 lint 某个函数会以不同数量的参数调用，就在函数前放上注释 `/*VARARGS*/`。可惜，想让 lint 闭嘴有时很痛苦。比如，memcpy() 和 strcpy() 就是典型的、返回值几乎从不使用的函数。

为了检查库用法的一致性，lint 需要描述每个库的文件。这些文件的内容不过是子程序的桩：类型定义和参数声明。如果你做了个库，也不妨考虑做一个 lint 库。

编译程序时 lint 不会自动运行，但你应养成经常使用它的习惯。它是 C 程序员最有用的工具之一，追查 bug 时能迅速把你引向正确方向。lint 由 Steve Johnson 编写。

## 7.3.7 curses

UNIX 最初是在 Teletype ASR33 上长大的。那是些机电怪兽，以惊人的 110 波特（每秒十个字符）输出字符。UNIX 的简洁风格，很大一部分源于此（“tty” 这个称呼终端的老词也源于此）。玻璃 tty（即哑 CRT 终端）行为像高速 tty，但仍然很“哑”。

UNIX 一向看重那些输出能作为另一个程序输入的程序，所以人们一般不肯花时间写图形应用——它们不合 UNIX 的范式。不过，有一个图形应用与众不同，那就是编辑。用 Teletype 编辑不是享受，用 CRT 编辑却是。Rand 编辑器已经证明了这一点。

Rand 编辑器一个比较恼人的缺点是，它必须针对每一种不同的终端做定制。1970 年代末，CRT 厂商有几十家，型号数百种，各干各的；要足够快地给每种终端写出支持例程（更别说调试）根本不可能。伯克利的答案是 termcap。

termcap（terminal capabilities，终端能力）是一个支持与终端无关的字符图形的库。它用一个简单的数据库描述系统支持的每一种终端，支持三百多种终端，而且数量还在不断增加。添加新终端相对容易。termcap 在管理员一章有进一步介绍。

curses 是 termcap 系统的高层接口，给用户提供直截了当的命令：比如 box() 在屏幕上画一个框，printw() 打印格式化字符串。使用 curses 的基本思路是，程序员只管描述屏幕应该是什么样子，curses 负责让物理屏幕真的变成那个样子——而且是以最优方式。

比如，假设你在显示一页数据，程序即将用新的一页重写屏幕，但两页数据除了页码之外完全相同。那么 curses 只会重写页码。curses 还会尽量用最少的字符插入和删除来完成更新——比如，数据已经在屏幕上，只是需要挪个位置。在慢速终端上看 curses 干活很有意思，因为它的做法反直觉（但很快）！

curses 还有提供初级窗口功能的函数。虽然 curses 局限于字符图形应用（包括画线字符和颜色），它已被大量使用，并移植到许多其他操作系统。Ken Arnold 的论文《Screen Updating & Cursor Movement Optimization: A Library Package》进一步描述了 curses，可从伯克利获取。

## 7.3.8 编辑器

> “我能找到 vi 的唯一用处，就是在把 emacs 源码移植到新机器时编辑这些源码。”——Larry Campbell

严格说来，编辑器不算编程工具。然而，许多程序员在开发程序时，大部分时间都在用编辑器；此外，许多编辑器带有工具接口，可以从脚本或管道中调用。

关于 UNIX 编辑器的讨论，都必须从 ed（Ken Thompson 编写）开始——UNIX 编辑器的老祖父。ed 在许多方面都很特别。即便你永远不用它（这不大可能），也值得学一学，因为某些紧急情况下会用到它。比如，你在硬拷贝终端上，或者 **/etc/termcap** “坏了”，就用不了屏幕编辑器；如果你无法挂载任何文件系统分区，那除了 ed 就无编辑器可用。

懂 ed 的另一个好理由，是你能用流编辑器 sed——它能在管道或脚本里做编辑，而 sed 的命令语言与 ed 非常相似。许多别的工具也从 ed 借用了命令：比如，大多数 UNIX 工具使用的正则表达式模式匹配，最早出现在 ed 里。ed 还开创了许多风格惯例，比如用“叹号”表示法在子 shell 里运行命令。ed 做了那么多漂亮事，它的源码当年甚至作为 UNIX 阅读材料之一分发。可惜由于许可限制，这已不可能了。

大多数 UNIX 版本都包含一个叫 vi 的屏幕编辑器。vi 由 Bill Joy 编写，是第一个使用 curses 的应用。vi 在早期 UNIX 用户中大受欢迎，因为它基于（你猜对了）ed。vi 后来成了 AT&T 的标准屏幕编辑器。我们建议你学它，理由很简单：它是所有 UNIX 系统上唯一都有的屏幕编辑器。

ex 是 vi 的一个版本，专为硬拷贝终端设计。它也像 ed，但共享 vi 的全部扩展命令。ex 同样在所有 UNIX 系统上都有。

许多人非常讨厌 vi，因为它重度依赖模式：你要么在插入文本，要么在执行命令。既然移动光标也是一条命令，你就得从插入模式切到命令模式才能移动光标。如果你打字时常要移动光标，就得敲一大堆切换模式的序列；而你要是停下来想会儿事情，可能就忘了自己在哪个模式。文本突然被当成命令执行，那才叫恼人。

我们推荐用 emacs 取代 vi，作为通用编辑器。emacs 没有 vi 那种沉重的模式包袱，还能同时在屏幕上显示多个窗口。可惜它不随 UNIX 分发，你得从第三方获取。尽管不便，许多人还是转向了 emacs（至少是离开了 vi）。最近一次 Usenet 投票显示，大约一半 UNIX 用户用 vi，一半用 emacs。

> **vi 里的多窗口？**
>
> Bill Joy 其实已经把多窗口做进 vi 了，甚至还在考虑让它可编程。后来怎么样了？
>
> 他添加多窗口支持的时候，磁带机坏了，又没有备份。Bill 照旧干活，直到有一天他的磁盘被“碾碎”了。他既没有备份，也没有完整的清单，只好放弃。之后，他退回上一个版本，写完手册，vi 就到此为止了。接着奔向下一个项目……

emacs（以及 mince 之类的类似编辑器）的强大之处在于它完全可编程（又是一门要学的语言）。emacs 很容易配置成新闻和邮件的前端，但我们见过有人走得那么远，竟用它来求解一阶谓词逻辑问题。

emacs 一个特别有用的特性是，它能编辑正在进行的 shell 会话！这意味着你在跟 shell 对话时可以使用全部编辑命令。此外，你可以滚动浏览整个会话、保存它，或者做任何对静态文件能做的事。

emacs（不是 “emacs makes a computer slow” 的缩写，而是 “editor macros”）最初由 Richard M. Stallman 在 MIT 写成，当时是跑在另一个编辑器（teco，不在 UNIX 上运行）之上的一组宏。CMU 的 James Gosling 为 UNIX 重写了 emacs。有意思的是，Gosling 没有移植 teco，而是选择把 emacs 架在一个小型 Lisp 解释器之上。

市面上有几种不同的 emacs 商业版本，其中一些并非基于 Gosling 的 emacs（俗称 Gosmacs）。GNU Emacs 是特别流行的一个版本，可从自由软件基金会获得。

选一个自己用着顺手的编辑器很重要。许多 UNIX 工具依赖编辑器来完成工作：比如，邮件程序在你写信时会自动启动编辑器。程序通常会到环境变量 EDITOR 里找你所用编辑器的名字。比如，csh 用户会在自己的 .login 文件里加入下面一行：
