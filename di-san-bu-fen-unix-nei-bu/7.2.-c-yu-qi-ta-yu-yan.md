# 7.2 C 与其他语言

> “你越早动手写代码，程序花的时间就越长。”——Roy Carlson

研究用的 UNIX 系统通常自带许多语言，包括各种实验性语言；商业 UNIX 系统通常只带很少几种——有些甚至把 C 语言也拆出来单卖——但几乎任何语言，都能买到在 UNIX 下运行的解释器、编译器和环境。

一个典型的 UNIX 站点往往会弄来几十种编程语言：C、Modula 这类高级语言，Ada、Smalltalk、Lisp 这类高层环境，yacc、lex 这类“小语言”，再加上各种 shell 这类面向用户的语言。

每种语言各有长短。信不信由你，一个优秀的 UNIX 程序员对它们都很熟练。每设计和实现一个项目，有经验的程序员都会挑选最合适的工具来解决问题——这正是优秀程序员的标志。

几乎任何语言，包括 C、Modula-2、Snobol、Forth、BASIC、Pascal、Lisp、Ratfor、Icon、APL、汇编、Ada、PL/I 和 Fortran，都能找到在 UNIX 下运行的解释器和编译器。（厂商信息见讲应用的章节。）其中不少在早期 UNIX 系统里就有，不过大多被形容为“只完成了 90%”。

这话相当准确，也不难理解：这些活儿不是由必须支持产品的商业公司干的，而是为了让没人愿意重写的老应用能编译而写的。通常，编译器或解释器不必支持整门语言，只要支持老应用用到的那部分就够了！还有几种语言来自课程项目，之所以被采用，纯粹是因为需求太大、人们对任何接近该语言的东西都很满足，哪怕只是部分实现。

当然，最早可用的语言是汇编器，然后是 C 编译器。两者都是完整实现，尽管谈不上特别精巧。尤其是汇编器，当年（如今也一样）相当原始。因为人们用它写的代码太少（大多数活儿都交给 C 编译器），它甚至一直不支持宏。

有了 lex 和 yacc，语言开发很早就繁荣起来。人们写了许多实验性语言，其中包括几个强大的宏预处理器，如 m3、m4 和 m6。它们可用于任何语言，比如汇编，但在 C 和 Fortran 圈子里特别流行。到第 7 版时，Fortran 66、BASIC 和 Snobol 的实现已经存在。

Fortran 77 紧随其后；到那时，伯克利的人已经提供了 Pascal、Lisp 和 APL 的实现。此后无数语言来了又走。随着 UNIX 普及到厂商愿意提供并支持几乎所有主流语言的完整实现，这些“学生作品”大多消失了。

在其他系统上，Fortran 被视为计算机的通用语言；而在 UNIX 上，Fortran 很少用于新应用。不过，大多数 UNIX 系统仍带有 Fortran 编译器，纯粹是因为现存的 Fortran 应用代码实在太多。

大多数操作系统都有唯一的主要实现语言，比如 Lisp 机器上的 Lisp，或 IBM 370 系列上的汇编。UNIX 也不例外。

历史上，C 语言一直是 UNIX 系统上的首选实现语言，原因有二：其一，厂商总得有一份 C 的实现——UNIX 系统本身就是用它写的；其二，大多数 C 编译器生成汇编，但与汇编（一般所有 UNIX 系统都有）不同，C 是高级的、可移植的，而且能轻松完成系统编程任务。

## 7.2.1 C 与 UNIX：共生关系

> “鸡是蛋想出来的、用来下更多蛋的主意。”——Samuel Butler

C 和 UNIX 关系特殊：UNIX 是用 C 写的，C 是专门为写 UNIX 而设计的。当初决定用 C 实现 UNIX，非常大胆，但已经一次又一次地得到了回报。

有些人不喜欢 C。有人说它是一门烂语言，全靠搭上一套好操作系统的顺风车才功成名就。这话不对。C 是一门伟大的语言：它在“必需”与“过度”之间取得了平衡（对比一下 Ada）。C 易于实现，却囊括了现代高级语言的全部精髓——结构化控制流、作用域、数据结构和模块化。它能为大多数类型的计算机生成高效的代码，又不强迫程序员为每种机器写出不同的代码。

C 虽为 UNIX 而生，后来却被一次次移植出 UNIX 环境。如今，C 在许多陌生的土地上枝繁叶茂：大型机、微处理器、单板机，甚至烤箱。凭借高效与可移植，C 已成为微机上特别流行的编程语言。总之，离开 UNIX，C 也证明了自己的价值。

这并不是说 C 没有缺陷。缺少类型范围、词法作用域偏弱、case 语句贯穿、break 的误用，都是设计问题的例子，也正是这些问题促使许多人提出改进 C 的标准。毫不奇怪，多数所谓“改进”方言要么自身有缺陷，要么彻底改变了这门语言的意图，结果更像 Ada。

虽然另有几种语言（如 Euclid、Modula-2）在 UNIX 系统编程上获得了一些人气，C 仍是构建 UNIX 工具的核心语言。许多工具主要就是为 C 服务的——比如 yacc 和 lex 都以 C 代码为输出。这样的输出可以并入任何项目，但在 C 里是举手之劳。

因为这些工具，C 常被视为许多应用的合理选择。可惜这种一概而论有时有害，因为 C 缺少某些类型编程所必需的支持：比如，C 不适合大规模数值计算（缺少溢出和下溢检测），也不适合表处理（缺少垃圾回收）。不过，几乎任何应用都能、也确实曾用 C 写出来。也许唯一绝对做不到的，是某些底层的机器操作，比如保存寄存器或弹出堆栈——但这类机器码小片段通常只需要写一次，比如写在编译器里。

我们不打算全面介绍 C（讲印刷资料的章节已推荐了几本好书），只想强调一点：C 语言已经成熟。可运行 C 编译器的机器比任何其他高级语言都多，用 C 写的新应用也比任何其他语言都多。计算机科学研究的头号刊物《Communications of the ACM》经常用 C 发布算法。任何想掌握计算机科学、更不用说 UNIX 的人，都必须熟悉 C。

C 的设计与标准化工作至今仍在继续。ANSI C 标准、C++ 以及其他 C 扩展，都是把 C 推向成熟现代语言的载体。我们预计 C 会活得长久而健壮。

当初用 C 实现 UNIX，要么是运气极好，要么是洞察极深。不管怎样，我们都大大受益了——无论对 UNIX 还是别的什么，它都是一门出色的系统编程语言。

## 7.2.2 库

> “只要有可能，就偷代码。”——Tom Duff

软件子程序库让程序员得以利用别的程序员的劳动。比如，你不必自己写清屏程序，因为已经有人写好了子程序（如 curses 库里的 clear()）。你要做的只是查对名字，然后调用。

大多数 UNIX 系统都带有大量库，包括字符串处理、数学、终端与窗口管理、通信等例程。好的程序员应当熟悉所有库和子程序——这样一来，实现项目所需的工作量会大幅减少。况且，库子程序通常比全新的代码可靠得多。

所以，在花时间写一个函数之前，先翻翻库：你正想写的子程序，也许早就有人写好了。

为了在构建程序时提高效率，子程序以目标代码形式保存；多个子程序又按类别组织成库（历史上也叫归档文件），以便高效、简洁地管理。ar（archive）命令用来创建和维护库。

程序链接时（把目标代码解析成机器可执行代码），目标文件和库被交给链接器，由它解析用户提供的目标代码与库之间的外部引用。

> **BSS**
>
> a.out 格式的文件由几个部分组成：一是可执行代码（称为 text），二是已初始化的数据，三是 bss。大家总问 bss 到底是什么、代表什么。答案如下。
>
> “bss” 代表 Block Started by Symbol（由符号开始的块）。这是如今已废弃的 IBM 汇编器使用的一个汇编伪指令，用来把一块内存填零——这正是 a.out 文件里 bss 的效果。bss 也叫未初始化数据。

UNIX 通常把库存放在预定义的目录里。**/lib** 一般存放 C 编译器所需的库：

* **libc.a**：标准 C 库——标准 I/O 函数、系统调用以及其他基础例程。C 编译器会自动包含它。

系统提供的主要库存放在 **/usr/lib** 里。（库之所以分放两个目录，原因和 /tmp 与 /usr/tmp 分放一样——解释见管理员环境一章。）**/usr/lib** 里的一些基本库有：

* **libF77.a**：Fortran 库——Fortran 运行例程。
* **libcurses.a**：字符图形库——用于创建与终端无关的字符图形工具的函数，依赖 termcap 或 terminfo 库。
* **libdbm.a**：数据库库——用于维护简单键值数据库的函数。
* **libm.a**：数学库——三角函数、对数及其他数学算法的函数。
* **libplot.a**：绘图库——用于创建与设备无关的绘图工具的函数，依赖把设备无关输出翻译成设备相关输出的逐设备绘图过滤器。
* **libtermcap.a**：终端能力库——访问和操作终端描述数据库 **/etc/termcap** 的函数。在 System V 上叫 “terminfo”。

你的系统上可能还有别的库——不同厂商会提供不同的库来支持特别功能。如果发现一个库让你好奇、又找不到文档，可以试试下面这招（假设库叫 libxyzzy.a）：

```sh
% ar tv libxyzzy.a
```

这会列出库的目录表。看到里面子程序的名字，通常就能猜出这个库是干什么的。

翻看存放库的目录，你还会看到同名但多一个字母 p 的库，比如 libc.a 和 libc_p.a。带 p 的版本用于对代码做性能剖析（见下文“性能剖析”）。这些子程序在开头和结尾有特殊语句，用来统计调用次数以及每个例程花的时间。

**/usr/local/lib** 是另一个目录，用户把自己想与同系统其他人共享的库存放在那里。链接器找库时会自动搜索这个目录。

## 7.2.3 C 预处理器

> “把我也排除在外。”——Sam Goldwyn

用 C 写的程序里常有大量以 # 开头的行。即便你不写 C，能读懂这些行也有用：许多程序的设计，使得可能发生的改动只需修改这些行就能完成。

以 # 开头的行是控制编译的指令。最初的 C 语言编译器在一个单独的预编译阶段处理这些行，这个阶段叫 C 预处理器，实现为一个单独的程序 cpp。大多数 C 编译器仍照此工作，但 C 语言标准并不要求必须把它实现成独立阶段，所以你不该依赖这一点。因此，“C 预处理阶段”是更合适的叫法，但出于历史原因，人们仍称它“C 预处理器”。

C 预处理器最重要的工作是代码替换。比如，你可以让预处理器在编译时把字符串 MAXMEMORY 替换成 2*1024*1024。用 MAXMEMORY 这样的字符串写程序，程序就能移植到任何系统；而直接写 2*1024*1024，程序就只能跑在有 2 MB 内存的系统上。

这种替换叫**定义**（define），因为它们以 #define 开头的指令出现。例如：

```c
#define MAXMEMORY 2*1024*1024
```

定义通常按主题归类，集中放在包含文件里。比如，所有与字符串处理有关的定义都在 **/usr/include/strings.h** 这个包含文件里。UNIX 系统在 **/usr/include** 目录下自带大量包含文件，每个文件以 .h 结尾。h 代表“头文件”，不过大多数人干脆叫它们“include 文件”。这些文件里往往有函数定义和原型、typedef、结构定义，以及简单的 define。

要把其中一个文件包含进你的程序（include 之名由此而来），就在 C 源码开头写一行 `#include <strings.h>`。尖括号是 C 预处理器对 **/usr/include** 目录的简写。想看看某个文件，可以 `cat /usr/include/strings.h`。浏览或用 grep 搜索包含文件，常常比读手册更有收获——它们才是最终的裁判，因为 C 编译器真正用的就是它们。令人沮丧的是，C 编译器不读手册。

预处理器还做其他一些事，包括剥掉注释，以及提供初级的流程控制语句来有选择地编译代码。条件编译是产生可移植代码的另一种办法。

C 预处理器在某些方面有局限。比如，它要照顾括号和字面量，并不是通用预处理器（尽管许多人拿它当通用预处理器使）。UNIX 的 m4 是强大得多的预处理器，超越了 cpp 的大部分局限。必要时，可以用 m4 替代 cpp。
