# 7.1 系统概念

UNIX 的优雅，很大一部分来自程序员可随意调用的那些函数的设计。它们往往是简单高效的例程：做一件事，并把这件事做好。比如 open() 对文件、目录和设备都管用。这些函数的一个子集就是系统调用。系统调用是与 UNIX 内核的接口，被视为 UNIX 系统真正的原语。比如，要写文件，用户必须使用 write() 系统调用。写文件还有许多高层接口（如 printf()），它们替用户屏蔽了编程中比较乏味的细节，但归根结底都会在某个时刻调用 write() 来干活。（从功能上说，系统调用和库调用没有区分的必要；好在它们在语法上看起来一样。）

系统调用定义并实现在一个特别的程序里，那就是内核（常被错拼成 “kernal”）。内核用 C 写成，但内核环境与大多数其他 C 程序截然不同：代码必须随时应对硬件中断；内存是全局共享的，类似一个多线程的单一进程。因此，每一段代码都得保护自己的数据结构，防止内核的另一部分同时访问。

应用程序并不常直接发起系统调用。系统调用是控制系统最高效的手段，却也相当原始。人们造出许多库，替程序员省下编码时间并提高健壮性。此外，库比 UNIX 系统调用更可移植。把程序移植到非 UNIX 操作系统时，你会发现高层调用通常比低层调用更容易模拟。

> **creat()**
>
> 有人曾问 Ken Thompson：“如果重新设计 UNIX，你会改什么？”他回答：“我会把 creat 拼出那个 e 来。”

## 7.1.1 I/O

UNIX 的长处之一，是它对待 I/O 的一致性。文件、设备乃至进程，都能用 I/O 原语来操作。UNIX 的 I/O 范式如此简单，学会了它，你就能轻松访问系统提供的大部分能力。

一开始可能让你困惑的是，设备常被称作文件。事实上，它们就是以普通文件名出现在文件系统里的。这其实是优点：把它们当磁盘文件看待，你就不需要专门的命令或函数。比如，设置设备保护属性的命令和语法，与设置磁盘文件完全一样；重定向也管用。如果你敲 `who > /dev/tty33`，who 的输出就会出现在 33 号终端上。

戴上 I/O 的有色眼镜看，UNIX 就像下图这样。后面的讨论会反复回到这张图。

```
应用程序
   │
 stdio
   │
 内核 ── 系统调用 ── 设备驱动程序 ── 设备
```

> **译注**：原图自上而下分为应用程序、stdio、内核、设备驱动程序、设备几层，并在内核对应用程序之间标注“系统调用”。内核与设备驱动程序之间也是类似的接口，应用程序与 stdio 包之间也是类似的接口。

系统调用在用户与 UNIX 内核之间提供了一层干净的接口；内核与设备驱动程序之间也共享类似的接口；应用程序与 stdio 包之间同样如此。

### 7.1.1.1 普通文件与目录

普通文件是存放在文件系统里的一串字节。除了简单的字节线性顺序，文件系统不对文件强加任何结构。用户不给文件显式设定大小；只要写到文件最后一个字节之后，文件就自动变长了；试图读过最后一个字节，则会返回文件结束（EOF）。文件也可以显式缩短。用户打开文件后，可以移动到文件的任意字节处读写（前提是有相应权限）。

没有文件结构和大小限制，正是 UNIX 的亮点。没有什么专门读取特殊结构的特殊文件的工具，因为压根不存在这种文件——所有文件都是简单的顺序文件。当然，用户可以自己约定工作规则，比如存放源码的文件通常只含可打印 ASCII 字符、每行以换行符（ASCII NL）结尾；但文件系统并不通过任何机制强制这一点。

每个文件都对应一个索引（i-number，i 号），它指向文件系统内部的某个数据字段。这些字段叫 i 节点（i-node），记录着文件的保护属性、长度、属主，以及指向存放实际数据的其他 i 节点的指针。i 节点不包含文件名。

目录是包含文件名列表的文件；每个文件名都关联一个 i 号。取出对应的 i 节点，就能到达该文件名所指的文件。给定文件名时，内核会自动完成这层映射。一般来说，程序员不必在这个层次上跟文件打交道，但这种表示法有两个重要后果：

1. 一个文件可以有多个名字，每个名字叫一个**链接**（link）。

2. 仅凭 i 号不可能查出文件名，除非彻底搜索。名字可能不止一个，甚至可能一个都没有（管道就是如此）。

每个目录本身也作为文件出现在文件系统中，因而可以出现在另一个目录的文件列表里——这就提供了 UNIX 文件系统特有的分层结构。目录可以被用户读取，但只有通过特殊系统调用才能写入，因为随意引用任意的 i 节点可能毁掉整个文件系统。在“文件系统不关心文件内部结构”这条规则面前，这是少数例外之一。

### 7.1.1.2 设备

UNIX 做的很多事就是控制设备，包括终端、磁带机、磁盘驱动器和网络接口。任何外设在 UNIX 眼里都是设备。UNIX 把设备分成两类：块设备和字符设备。

块设备以固定大小的字符块进行 I/O，磁盘是典型代表。字符设备不受固定块大小的限制，一次可以传输任意多个字符（包括单个字符），键盘和鼠标是很好的例子。其实也可以把磁盘当字符设备对待，但那样通常效率不高。

执行 `ls -l /dev` 就能看到系统里哪些设备是字符设备、哪些是块设备：第一列的 b 表示块设备，c 表示字符设备（d 表示目录，- 表示普通文件）。对多数程序员来说，设备的类型并不重要——高层库把它们统一起来，用起来一个样。

一个设备可以同时被当作字符设备和块设备。比如磁盘通常按块访问；但复制磁盘（如备份）时，按字符设备访问效率更高——字符设备一次能传输任意多个字符，而块设备受块大小限制；而且块设备在内核里要经过缓冲，字符设备则不必。

有意思的是，内存也能作为设备访问——不过这更像一扇后门，而不是什么正经主意。走 I/O 系统（通过系统调用）去跟内存打交道，比直接（用一条机器指令）访问的开销大得惊人；但用这种方式，可以访问本来受保护的内存。比如 ps 就是通过读取 **/dev/kmem**（内核内存）和 **/dev/mem**（物理内存）来挖出其他进程的信息。

设备（见上一节的图）不算 UNIX 本体的一部分，而是位于它底下——正如运行 UNIX 的计算机本身并不被称作“UNIX 计算机”。任何设备都能纳入 UNIX，只是有些设备比另一些更合适。比如，上电时开着中断的设备就让人恼火，也不符合 UNIX 的脾气。想读点 UNIX 与现实世界设备冲突的趣文，可以看 Tom Lyon 与 Joseph Skudlarek 的《All the Chips that Fit》，载于 1985 年夏季 USENIX 会议论文集。

### 7.1.1.3 设备驱动程序

每个设备都有一个专门的程序，向 UNIX 系统呈现一套接口。这个程序叫**设备驱动程序**（device driver），它让各个设备“表现得”一个样。具体来说，驱动程序可以令设备看起来像字符设备，或者像块设备。

每一类设备都由一组可以在它身上执行的小函数定义，其中大多数直接对应系统调用。比如，每个设备都有 open()、read() 和 write() 调用。设备以文件形式出现在文件系统中，通常在 **/dev** 目录下；访问这些文件时，内核就调用与各自关联的例程。（例程是如何选中的，管理员一章有进一步说明。）

结果就是：通过对文件系统的访问，所有对象的访问方式被统一起来。比如，从磁盘文件读和从键盘读一样容易，因为两者对 read() 系统调用的反应相同。除了经由定义良好的接口，访问设备是被禁止的——这就提供了一个可靠的设备子系统。

**伪设备**（pseudo-device）是有驱动程序、却没有对应实体的理论设备，你可以把它们想成模拟出来的设备。伪设备用来实现管道和许多网络设备。最简单的伪设备例子是 **/dev/null**。

> **空设备——/dev/null**
>
> /dev/null 是 UNIX 系统里最简单的设备。往里写，字符就被丢掉——实际上是完全忽略，write() 直接返回成功状态。当你不在乎一条命令的输出、只关心它的副作用时，这很有用。（比如 `time grep a /usr/dict/words > /dev/null` 会打印出搜索所有含 a 的词花了多少时间；若不加这个重定向，它还会把那些词本身也打印出来。）每当读取 /dev/null，它都会产生 EOF（文件结束）状态。
>
> /dev/null 的另一个主要用途是在消息里，比如：“系统中午停机。有意见请寄往 /dev/null。”

**管道**

另一个伪设备是 UNIX 管道。和任何设备一样，管道可以打开、读取和写入，但没有对应的物理外设。往管道里写时，字符在内存中缓冲，直到有人从另一端读取。正因如此，它特别适合充当两个进程之间的通信通路。

当把命令 `who | lpr` 交给 shell 时，shell 创建两个进程，并在它们之间架一根管道：who 往管道里写，lpr 从管道里读。注意，who 没有什么访问管道的特殊参数，lpr 也没有；两个程序都没有试图检测自己正在使用管道。

管道由管道设备驱动程序缓冲。如果写端比读端快，驱动程序就拦住写端，直到管道排空一些；同样，管道为空时读端会等待写端。写端关闭输出流后，读端会收到 EOF（就像从磁盘读文件到头一样）。

这个简单的设备，正是让 shell 能把程序插接起来、而无需事先专门编码的关键机制之一。

管道的一条限制是：管道的两端只能通过执行进程的共同祖先来继承。在 shell 里用管道没问题——shell 就是那个共同祖先，把管道的两端分别交给不同进程；但这让毫无关系的进程没法通信。UNIX 后来加入的机制（即套接字和流）克服了这一限制。

**命名管道，即 FIFO**

命名管道是 UNIX 的一项扩展，最初出现在 PWB 中，直到 System V 才普遍可用。命名管道和普通管道一样，只不过它有名字。因为它出现在文件系统中，任意进程都能引用它，从而为互不相干的进程提供通信手段——这就克服了普通管道的限制。命名管道又叫 FIFO（“First In, First Out”，先进先出）。

遗憾的是，命名管道并没有为客户端-服务器模型提供简单的解决方案。比如，服务器打开一个命名管道等待客户端时，它必须有办法防止或区分两个不同进程写进同一管道的数据。

在互不相干的进程之间通信这件事上，套接字和流提供的机制都比命名管道更好。

### 7.1.1.4 基本 I/O 系统调用

前面提到的所有设备都实现了同一套基本系统调用，包括 open()、read()、write() 和 close()。大多数程序需要的也就这些。shell 执行程序时，会为每个进程自动创建并打开三个文件。文件一旦打开就称为**流**（stream），并用**文件描述符**（file descriptor）来指代。为每个进程打开的这三个流是：

* **标准输入**：提供输入的流，比如来自终端或管道中前一个进程。文件描述符 0，文件指针 stdin。
* **标准输出**：供输出的流，比如送往终端或管道中的下一个进程。文件描述符 1，文件指针 stdout。
* **标准错误**：供错误信息的流，免得它们在管道中被意外重定向。文件描述符 2，文件指针 stderr。

拿 `who | lpr` 这个例子来说，who 的 stdout 会自动接到一根管道上，管道的另一端接到 lpr 的 stdin。who 不读任何输入，所以会忽略自己的 stdin；lpr 把结果打印到 stdout，也就是终端。两个进程的 stderr 也都是终端。

听起来复杂，其实很简单，大部分活儿 shell 都干了，进程甚至不必调用 open()。who 要做的只是用文件描述符 1 写出结果，lpr 则用文件描述符 0 读取。

read() 和 write() 的调用很直白：

```c
cc = write(1, buffer, length);   /* 在 who 中 */
cc = read(0, buffer, length);    /* 在 lpr 中 */
```

read() 从 stdin 读取，最多把 length 个字符放进 buffer；read() 返回时，读到的字符数存在 cc 里。write() 的工作方式类似。

这看起来简单，却相当原始，对大多数类型的处理来说效率也不高。原因在于，如果一个进程每写一个字符（甚至每一行）就调用一次 write()，那么每次调用都要和内核做一次上下文切换。通常可以对 I/O 做缓冲：让字符排队，直到达到某个高水位，再用一个大缓冲区调用 write()。这样能减少系统调用次数（以及相应的上下文切换）。

### 7.1.1.5 标准 I/O

标准 I/O 是一个库的名字，它为我们刚讲过的 I/O 系统调用提供了更高层的接口（见前图）。它更好用，同时灵活得多。标准 I/O 通常缩写为 “stdio”（读作 “stud-i-o”），因为在 C 程序里用 `#include <stdio.h>` 这一行来引入它的相关定义。stdio 基于贝尔实验室 Mike Lesk 的“可移植 C 库”：该库通过提供统一的 I/O 系统，让 C 程序能跨不同操作系统保持可移植。凡是有 C 编译器的机器，都能实现 stdio。

和系统调用一样，stdio 非常干净，因为它对文件系统中的所有对象——磁盘文件、设备、伪设备——一视同仁，并且遵循 stdin、stdout、stderr 的约定。

stdio 库与系统调用的一个显著区别是，高层的 stdio 函数带缓冲。对应 open() 系统调用的是 stdio 的 fopen()：fopen() 打开文件，并在用户空间分配一个 I/O 缓冲区。往缓冲区里写字符（或从里面读）非常便宜；缓冲区满了就冲刷出去。这对程序员是透明的，只是程序跑得飞快。而且由于缓冲由库调用来处理，程序在变得极其高效的同时仍保持可移植。

对终端做 I/O 时，stdio 会改变缓冲策略，好让用户不必等整个缓冲区填满才看到东西。（程序员也可以显式控制缓冲。）输入缓冲的工作方式类似，相比 read() 提供了相应的效率优势。

stdio 用起来比系统调用还简单。write() 需要三个参数，fprintf() 只要两个（而且 fprintf() 还能做复杂的高层格式化）：

```c
write(1, "hello, world", 12);
fprintf(stdout, "hello, world");
```

stdout 是保存输出流缓冲区的 stdio 结构的名字。由于向 stdout 打印太常见了，printf() 就是它的简写：

```c
printf("hello, world");
```

### 7.1.1.6 更多的设备驱动程序

**终端（tty）——/dev/tty**

任何系统里最复杂的设备驱动程序之一，都是终端驱动（通常写作 tty，读作 “titty”）。它控制终端以及其他通过 RS-232 接口连到系统上的东西。这些东西的工作方式差异多得惊人。

为了让终端接口现代化、同时仍支持老程序，人们做了各种尝试，结果把终端驱动搞得复杂无比。人类学家若想研究这个驱动的历史，看看它那古怪的接口大概不难还原。它的复杂也许未必合理，但很可能比任何别的操作系统的终端接口都灵活。

终端可以像普通文件一样读写。当 shell 提示终端输入命令时，它不过是在打开一个文件、从里面读字符、再往里写字符。shell 读到文件结束时，就停止处理命令并退出。因此，你可以通过给 shell 发一个文件结束符（通常按 control-D）来登出 UNIX。近年的 UNIX 版本还加了 logout 命令，效果相同。

**原始模式**

终端驱动之所以复杂，一个原因是它必须在把每一次击键交给程序之前先检查一遍。比如，按空格键也许只是把空格送给程序；但 control-C 必须变成中断，退格则真要把前一个字符从输入流里删掉！诸如此类的复杂性，别的驱动都不必操心。

程序可以要求驱动不对击键作任何特殊解释。这叫**原始模式**（raw mode），因为程序看到的是用户敲下的原始击键。屏幕编辑器常用这种方式。

当驱动对字符作解释时，称为**熟模式**（cooked mode）。对这整件事，有点幽默感是有帮助的。

**伪终端——/dev/pty**

另一个伪设备是 pty，即伪终端。pty（读作 “pity”）的行为和 tty 一模一样，只不过 I/O 并不发生在任何物理设备上，全都在 pty 驱动的想象中进行。典型用途是支持通过网络登录：用户会话看起来具备串行线路控制器的全部特征，但一切都是模拟的。

pty 总有一个对应的 tty 与之通信。模拟出来的终端（主端）总是 pty（比如 **/dev/ptyp2**），而我们想象中通过串行线连接的程序（从端）则使用对应的 tty（**/dev/ttyp2**）。换句话说，写到主端的数据会作为输入交给从端，就好像它来自硬件接口（如 UART）一样；相应地，写到从端的数据可以从主端读出，就好像它被送往硬件接口一样。

**套接字**

伯克利 UNIX 从 Arpanet 社群引入了套接字（socket）的概念，以支持 TCP/IP 网络。套接字还提供通用的进程间通信——比如，管道式的通信就是用套接字实现的。

套接字是通信端点，很像文件描述符。事实上，它们就是作为文件描述符、用 read()、write() 这类完全相同的系统调用来操作的。不过，套接字上还定义了额外的系统调用，以支持网络寻址、互不相干进程间的通信等更多能力。只需稍加扩展，现有程序就能改用套接字重写，结果是它们能与别的系统上的进程通信。

除了管道式通信，套接字还能用于服务器-客户端通信，以及消息传递或虚电路。套接字可以支持任何网络协议，包括 DoD 的 TCP/IP 和 ISO 标准；不过，每种网络都需要不同的套接字协议解释器。

**流**

流（stream）最早在第八版中实现，用来统一控制终端处理的各种复杂线路规程；后来被推广到进程间通信。因此，流能解决伯克利当年用套接字解决的同样问题——即互不相干进程之间、以及跨网络的通信。以这种形态出现的流，最早被引入 System V。

流与套接字非常相似：它们都是通信端点，都能用常规程序和系统调用来操作；流以常规文件的形式出现在 UNIX 文件系统中（尽管是在 **/dev** 目录下），就像 UNIX 域套接字一样。当两个程序打开同一个设备时，它们就能通信。

进程一旦建立通信，就可以在流上传递文件描述符（在互不相干的进程之间），这使得编写服务器变得非常容易。

网络驱动不再以专门的设备驱动程序出现，而是作为等待通用流设备的内核或用户级服务器。为了用某种协议通信，程序通过库调用把模块“压入”流中。模块可以层层堆叠，从而支持多层协议。

伯克利的套接字和 System V 的流听起来不同，功能上其实是一对孪生子。对实现者来说差别显而易见，对应用程序员则远没那么明显。事实上，只要功夫下够，任一系统都能模拟另一个。未来的 UNIX 系统很可能两者兼有。不过，流格外优雅，可能会成为未来进程间通信的主导基础。

**其他驱动**

给 UNIX 添加新驱动相对容易，你只需为驱动提供一组被访问时执行的调用（open()、read()、write() 等），再把这些例程链接进内核（内核通常正是为此以目标文件形式分发）。

由于驱动运行在内核的同一地址空间里，它能摆布系统的任何部分，包括任何用户进程乃至内核本身。于是，设备驱动成了一条捷径，让 UNIX 去做设计者从未通过系统调用允许的事情。比如，早期 UNIX 只提供小到一秒的定时精度；常见的变通办法是写一个驱动，提供毫秒级的睡眠能力。如果你想睡比如 17 毫秒，就写 `write(fd, buffer, 17)`——缓冲区其实不写到任何地方，但驱动会等上 17 毫秒再把控制权交还进程。

驱动程序还被用来实现文件和记录锁，以及别的更有想象力的事情——那些 UNIX 从未设计来处理的事。设备驱动提供了极其干净的接口，但正如上面的例子所示，它们也很容易被滥用。

## 7.1.2 进程

UNIX 支持多进程（执行程序的环境）。多进程对每个程序是透明的：各进程各跑各的，互不理会。用户常常利用多进程（比如在管道里启动好几个程序），而进程本身不必操心别的进程，因为不管有没有别的进程参与，I/O 看上去都只是读写一个简单文件。不过，进程也可以显式创建或管理其他进程——比如 shell 就替用户这么干。

程序在执行之前按常规方式构建：编译、链接，得到一个机器指令可执行文件。内核可以用 exec() 系统调用执行这个文件：内核用新程序覆盖调用程序，并把进程的控制权交给它。新程序从祖先那里继承若干东西，包括已打开的文件。shell 正是利用这一点，把自己的 stdin、stdout、stderr 传给新进程。如果用户在管道里启动了程序，shell 会创建管道，并把管道的一端交给每个程序。

> **魔数**
>
> 当程序被 exec 时，内核会读取文件开头的几个字节，与若干魔数比对。这些魔数是已知常量，用来标明文件是机器码还是 shell 脚本。为了区分不同的 shell，你可以在文件开头写上 `#! shellname args`。内核看到这一行，就会用你的文件作为输入来运行 shellname；如果它认不出任何魔数，就假定这是 /bin/sh 脚本。请在所有 shell 脚本开头写上这样一行，好让人清楚你的脚本是为哪个 shell 写的。
>
> 可执行文件是 UNIX 中少有的、内核会检查文件特定内部结构的情形之一。

exec() 有若干不同形式，尽管真正的系统调用只有一个（其余是库版本）。用哪一种取决于你想怎样传递参数。（真正的系统调用是 execve()，但人们在口头交流时大多称它为 exec()，即最早的那个。）

exec() 能运行新程序，却不能创建新进程。新进程用 fork() 创建：fork() 复制当前进程，新进程称为原进程的子进程，父子双方继续运行。

shell 通过 fork 创建新的用户进程；然后，子进程（仍在运行 shell）用 exec() 让用户程序覆盖自己。如果 shell 发现自己身处管道之中，它会在 exec() 之前把 stdin 和 stdout 换成管道的相应端。

wait() 系统调用让父进程等待子进程退出（另外还有 exit() 系统调用）。如果用户要求某个进程异步运行（在命令末尾加 &），shell 就不调用 wait()，而是直接提示下一条命令；否则 shell 就调用 wait()。于是，异步或同步处理都轻而易举。

每个进程都有一个进程号（pid）。pid 是可用于与对象通信的描述符。比如，知道进程的 pid，就能给它发信号；前面提到的 wait() 系统调用就以 pid 为参数。

进程还可以用进程组号分组，这对向一组相关进程发送信号很有用。比如，这让你一登出就能杀掉自己的各种杂项进程。

人们曾试图把进程和文件统一起来（很像物理学的大统一理论）。其中一种做法出现在 UNIX V8 中，并在 SVR4 里可用：每个进程都作为文件出现在文件系统中，比如 **/proc/17** 就是 pid 为 17 的进程。通过打开并修改这个代表其内存映像的文件里的字节，就能调试该进程。

即便没有这种进程与文件的统一，UNIX 的进程管理也出奇地简单直接：调用没几个，参数也不多。

回到 shell 的例子：有意思的是，每个 shell 最终都会退出（当用户登出或敲 EOF 时）。调用 shell 的进程 init 会收到通知，然后回去监视终端或调制解调器，等待新用户。若有新用户登录，init 会再次通过 fork() 和 exec() 为该用户创建新的 shell。（这个过程在管理员一章有进一步说明。）

## 7.1.3 信号

> “这页手册让人困惑。”——伯克利 UNIX 手册中 sigvec 的 BUGS 一节
>
> “这页手册还是让人困惑。”——同一手册的下一个版本

信号是软件中断。信号可以由硬件条件（如除零、寻址异常）或显式请求（如另一个进程请求该进程停止）产生。完整的信号列表见 **/usr/include/signal.h**。

程序可以声明收到大多数信号时要采取的动作，比如恢复或清理。未被捕获的信号通常会导致进程终止。某些信号，如 SIGKILL，是进程无法捕获的——给进程发 SIGKILL 是杀掉它的可靠办法。SIGQUIT（可按键盘上的某些键产生）会杀掉进程并生成“核心转储”（core dump），这对调试失控的进程特别有用。

“核心转储”这个词是历史遗留，指的是用磁芯作主存的年代。现代计算机已不用磁芯，技术变化这么快，“内存转储”本该更贴切，但人们似乎舍不得改口。

信号也可以在内部产生，比如由闹钟（SIGALRM）或 I/O 就绪条件（SIGIO）产生。这为某些类型的问题提供了极其高效的编码手段——比如，用 SIGIO 可以避免轮询。

不幸的是，早期的信号实现很难用。比如，信号不会排队；它们会打断系统调用（这意味着每次系统调用后都得检查是否被打断），等等。一个尤其要命的问题是：信号发生时，它做的第一件事就是把处理动作重置为默认行为。如果在进程重新设置之前又来了一个信号，程序就会错误地终止。

伯克利在 4.2BSD 中弥补了这一点。可惜，这个方案与早先的 UNIX 信号版本相当不兼容。于是你只能在两者中选：标准但不可靠的信号，或者可靠但不标准的信号。System V 最终吸收了伯克利信号的大部分特性，既减少了主要的可移植性问题，又获得了可靠的信号——可惜接口一点也没变简单。伯克利那页描述信号的手册至今在 BUGS 里写着：“这页手册还是让人困惑。”

大多数信号由内核产生。不过，只要有权限，任何信号都能用 kill() 系统调用发给任何进程。kill() 除了发信号杀进程，很少作他用，其名字也由此而来。只是很难理解，当初为什么不把它叫作 sendsig() 之类更合理的名字。
