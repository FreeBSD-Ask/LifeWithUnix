# 8.2 管理磁盘

> “去找大师吧。”——fsck 文档在收到某些错误时给出的建议

UNIX 的分层文件系统在概念上干净，实现起来却相当复杂。原因有几个：其中之一是要在一片光怪陆离的设备之上提供干净的接口；另一个是在系统崩溃时仍能维护文件系统的完整性。

## 8.2.1 挂载与卸载文件系统

概念上，UNIX 文件系统是一棵树。不易察觉的是，树的枝干可以坐落在物理上彼此分离的设备上。物理磁盘还可以在逻辑上分区，从而看起来像不同的设备。每个逻辑分区本身就是一个文件系统，但对用户来说，多个文件系统呈现为单一文件系统。

通常会留一个逻辑分区给交换空间（swap）。换页的意思是，进程可以被移出内存、暂时存到磁盘上，直到某个时刻再调回内存继续运行。当你有好几个进程无法同时装进物理内存时，这就很有用。

根文件系统 “/” 位于另一个分区。把 / 和交换分区分在同一块磁盘上，就能启动一套最小系统，而不依赖网络或任何其他磁盘。这让系统相当健壮，因为只要能启动一块盘就够了。

UNIX 启动后，就能挂载其他文件系统。它们被安放在仅作占位用的空目录上，真正干活的是 mount 命令。挂载的结果是：占位目录现在看起来就和那个新分区的根一模一样。用户看不到新根，只是把新文件系统看成又一个目录。

umount 撤销 mount 的效果。文件系统一旦卸载，用户就访问不到了；他们会看到原来那个空目录，这时你就可以把磁盘从系统中取走。

网络文件系统（如 NFS 和 RFS）扩展了 mount 和 umount 的语义。用它们，你可以挂载远程系统上的设备，让它们看起来就像本地文件系统的一部分。工作站就常用这一手：你坐到任何一台工作站前，都能从网络文件服务器上挂载自己的文件来访问。

## 8.2.2 维护文件系统完整性

文件系统内部相当复杂，但只要通过定义良好的接口访问它，你就不必操心。一旦系统崩溃，或者有人把电源线从墙上拔了，文件系统很可能“不同步”。比如，你正在删除一个文件时出了事，文件可能已从目录里消失，可它占用的空间还没有归还到空闲空间的池子里（也叫“空闲表”，freelist）。

系统启动时，每个文件系统都会在挂载前接受完整性检查。如果没检查就挂载了垃圾文件系统，系统在遍历数据结构时可能彻底失控。检查文件系统完整性的是 fsck（file system check）程序。

fsck 遍历文件系统底层的数据结构，验证其一致性；发现不一致，就尝试修复。文件系统里特意保存了一些冗余信息，正是为了这个目的。因此，fsck 总能修复不同步的文件系统。不过，如果问题由软件 bug 或硬件错误引起（比如控制器在某个随机扇区上乱涂了垃圾），fsck 就不大可能把磁盘恢复到完全健康的状态。当 fsck 发现问题且无法完美恢复时，它会通知你。比如，fsck 发现一些文件没有任何目录指向它们，就会给它们编个名字，放进 **/lost+found** 目录。

关于 fsck 有两篇出色的文章：讲 System V 的是 Michael Saxon 的《Using fsck》，载于 ;login: 第 10 卷第 3 期（1985 年 8 月）；讲 BSD 的是 Marshall Kirk McKusick 的《Fsck – The File System Check Program》，载于《4.2BSD UNIX System Manager’s Manual》。

> **这文件叫什么名字？**
>
> 文件并不连同名字一起存储。名字存在目录里，而且可能有不止一个名字指向同一个文件。
>
> 文件系统内部用索引号（i 节点号）标识文件，因为名字并不唯一。你可以用 `ls -i` 查出某个文件的 i 节点号，但除非把文件系统上所有目录都翻一遍，否则查不出一个文件的名字。
>
> 比如，要在 /usr 文件系统中找到 i 节点号为 20899 的文件，可以执行下面某条命令：
>
> ```sh
> System V% find /usr -xdev -inum 20899 -print
> Berkeley% find /usr -mntpt -inum 20899 -print
> ```

早期的文件系统没有现在这么健壮，fsck 也不总能修好。手工打补丁很常见，用的是 fsdb 这类专门的文件系统调试器，甚至用 adb。clri、ncheck、icheck 和 dcheck 属于一套对文件系统执行特殊操作（比如把某个 i 节点清零）的程序。好在如今这些程序很少用到了。

## 8.2.3 备份

> “可能出错的事，一定会出错。”——墨菲定律

备份文件系统的重要性，无论怎么强调都不过分。磁盘控制器一旦发疯，或者哪怕你只是误删了一个文件，备份都是唯一的恢复途径。**每天备份！**

备份通常用 dump 完成，不过还有其他一些保存文件的工具，包括 volcopy、dd、tar 和 cpio（不幸的是，这个清单因系统而异）。这些工具各用各的方式保存文件。它们彼此不兼容，看起来也许奇怪，但不同类型的备份自有其道理：格式不同，用途不同，各有优劣。比如，dump 适合备份文件系统，因为它会保存 i 节点信息；但 dump 磁带不适合分发软件——别的站点才不在乎你的 i 节点。这种场合下，tar 或 cpio 会是更好的选择。

备份通常执行很久，因为它必须记录整个文件系统。既然耗时这么长，用户就可能在备份期间写入文件，而这些文件没被记录——因为 dump 已经转储过文件系统的那一部分，新文件恰好在那一部分里。因此，待转储的文件系统应处于静止状态。

完整备份要占用大量专用时间和备份介质，所以大多数备份是增量的。增量转储只复制自上次备份以来发生变化的内容，通常比完整备份少得多。在用户环境一章里，我们给出过一个用 cpio 做增量备份的工具。

磁盘灾难之后，可以恢复备份——可以只恢复选中的文件，也可以全量恢复。如果做过增量转储，你就得依次恢复所有增量，直到一切看起来正常。

> **天哪，这文件可真大！**
>
> “有洞”（hole）的文件是通过跳过文件末尾再写入而产生的：旧文件末尾与新数据之间的部分都是洞——那里没有数据，也就不占磁盘空间。洞很好，只是并非所有工具都懂它。
>
> 有一天，一位程序员不小心把指针交给了 fseek，结果造出一个巨型空洞。du、df 这类常规文件命令都没受影响；可到了下一次备份，dump 却要了 26 盘 40 MB 的磁带——它只不过想保存那个位于 146 MB 分区上的 1 GB 文件！

用户误删文件时，备份也能派上用场：只要文件在上次转储之前就已创建，就能恢复。但得提醒用户，别把这事当成依靠——因为没法保证用户不是在最近一次备份之后才创建文件的。

备份是 UNIX 的薄弱环节，也是 UNIX 管理如此困难的原因之一。备份要求系统静止；UNIX 没有磁带库系统；没几个磁带工具懂多卷文件系统或多卷磁带。各版 UNIX 的磁带备份流程之所以各不相同，就是因为谁也没把它们做对。

UNIX 试图在一条细线上走平衡：既不要求操作员来管理备份，又强迫用户了解预防性文件系统维护的决策、问题和责任。随着磁盘容量增长、计算机系统越来越复杂，UNIX 必须拿出一个集成而精细的备份管理方案。UNIX 得长大了。

## 8.2.4 磁盘配额

UNIX 传统上生活在开放环境里，用户对自己的行为负责，对配额或资源记账的需求很小。

如今 UNIX 走向商业，买家开始要这些大型机上的老概念，于是 UNIX 有了配额。幸运的是，配额迫使 UNIX 清理了一些毛病。尤其是早期版本的 UNIX，总爱表现得好像永远不必操心文件空间：用户程序一旦失控，就可能吃光所有磁盘空间，系统随之 panic、崩溃。

其实，系统本身依赖可用文件空间的地方极少；可大多数程序员都盲目沿袭了“无视 write() 因磁盘空间不足而失败”的习惯。他们知道，自己的程序没空间了，系统也就没空间了；既然系统马上就要崩溃，程序是不是要转储核心，也就无所谓了。

## 8.2.5 符号链接

硬链接让人能把（可能多个）名字关联到同一个文件。这种链接只能指向已存在的文件，主要缺点是跨不了文件系统。比如，在某个系统里 /usr1 和 /usr2 可能位于不同的文件系统，你没法用一个以 /usr1 开头的路径名链接到 /usr2 里的文件并直接访问它。

伯克利的一项极其有用的创新是符号链接（symbolic link）。符号链接克服了硬链接不能跨文件系统的限制，让你可以创建一个指向 /usr2 中文件的链接，并让它出现在 /usr1 里。这解决了不少由来已久的问题。比如，你拿到一个程序（只有二进制），它非要把文件放进一个你没空间的文件系统分区；这时你可以从程序想要的文件名创建一个符号链接，指向你有空间的分区。当然，用得太多会把文件系统搞成一团乱麻。

符号链接也有别的毛病。比如，你从一个目录链接到另一个目录时，没法选择 ..（父目录）指向哪里；符号链接可以指向不存在的文件（尽管有人视之为特性）；而且与硬链接只有一套文件权限不同，每个符号链接都有自己的权限。

## 8.2.6 find 与 xargs

find 是大多数管理员忽视的一条用户命令——它手册页略复杂，因为语法不寻常。但知道怎么用 find 很值得，能省下你许多力气。

find 让你对整个目录层次执行任意操作。比如，你需要改一棵大目录树中每个文件的保护模式，可以手工来，也可以让 find 替你干。我们建议后者。

find 是可扩展的：你可以把操作限制在具有某些特征的文件上，比如属主、最后修改时间，以及许多其他参数。下面这行能让 find 删掉一周内没被访问过的所有目标文件：

```sh
% find . \( -name '*.o' \) -atime +7 -exec rm {} \;
```

find 的妙处在于，你能用它做出设计者从没想过的事。比如，它不限于 chmod 或 rm，可以执行任何命令，复杂度不限。

xargs 与 find 类似，只是它不专门用来遍历文件系统。xargs 从 stdin 接受文件列表，比如由 ls 甚至 find 生成的列表；它从 stdin 读取文件（以及更多参数），再对文件执行给定命令。比如，下面这条命令会提示用户选择要归档进 arch 的文件：

```sh
ls | xargs -p -l ar r arch
```

下面这条命令作为 shell 脚本运行时，会对成对的参数依次运行 diff：

```sh
echo $* | xargs -n2 diff
```
