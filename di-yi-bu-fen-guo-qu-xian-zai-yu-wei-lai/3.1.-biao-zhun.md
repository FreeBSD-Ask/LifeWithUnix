# 3.1 标准

> “标准这玩意儿的好处就是……选择多得很！”——佚名

1984 年，/usr/group 成功完成了“1984 /usr/group 标准”。该标准定义了 System III 内核调用与库调用的一个子集，外加一个记录锁原语。它立刻无人理睬，实际上毫无用处。问题在于，/usr/group 想标准化的领域当时仍在飞速演化：那时 V7 UNIX 还流行，但 BSD 已经做了大量改动，AT&T 又带着 System III 重新登场；更糟的是，UNIX 兼容产品正四处冒出来。XENIX 是 UNIX 吗？Coherent 是 UNIX 吗？到底什么才是 UNIX？

自那以后，UNIX 和 C 都没能立起成功的标准；不过到本书即将完成之时（1988 年初），看来不久的将来我们就能见到一些有用的标准了。在此期间，有些事实标准一边在用，一边在争取被采纳为正式标准。

许多标准虽然不是 UNIX 标准，关系也不那么直接，却影响着 UNIX 用户。比如你要搭一个由 UNIX 系统组成的网络，就该关注通信标准——因为你免不了要和遵循这种或那种网络标准的设备打交道。在数百个并非 UNIX 标准、却显然与 UNIX 用户相关的标准中，这是典型的一例。可惜我们不可能面面俱到，只好讨论那些直接影响所有人的标准，也就是 UNIX 标准和 C 语言标准。

如果你能用 Usenet，可以订阅 USENIX 赞助的审核制新闻组 comp.std.unix，或邮件列表 std-unix@uunet.uu.net（uunet!stdunix），来跟上 UNIX 标准的进展（要加入列表请写信给 std-unix-request）。大多数标准组织都有成员在读这个论坛、为它投稿。

## 3.1.1 C 语言标准

**K&R**

Brian Kernighan 和 Dennis Ritchie 的《C程序设计语言》（The C Programming Language，第一版）是第一本关于 C 的书，书中附有一份语言参考手册，后来人们便以两位作者之名，把它奉为“K&R C”的标准。

幸运的是，K&R 写得极其出色，语言定义里留下的暗角很少。但 K&R C 的设计本身有几个固有问题；此外，这门语言还有大量被普遍接受的扩展没写进 K&R（比如枚举类型）。

某种意义上，K&R 有点像《圣经》：有原教旨主义者，实现 C 的时候一字一句照办；有代言人，重新诠释神的教诲，做出（本人也承认的）“不太像 K&R C 的 C”；有异端，把问题歪曲得离谱，搞出混血方言还冒充 C，把新手程序员搅得晕头转向；当然，还有新时代的教派信徒，捧着 C++ 之类的另类教义来搭救我们。

**PCC**

K&R 虽然在大多数问题上没什么含糊，但还有个更高的权威——C 编译器本身。当 UNIX 跑在 PDP-11 上时，确实只有一款 C 编译器：Dennis Ritchie 的编译器。从 UNIX V4 到 V7，用的都是 Ritchie C 编译器。

随着人们对 UNIX 和 C 的兴趣高涨，贝尔实验室内外写出的新 C 编译器多了起来。其中特别值得一提的是 Steve Johnson 写的那个：它为可移植性而专门设计，名为可移植 C 编译器（Portable C Compiler），简称 pcc。相比之下，Ritchie C 编译器的可移植性并不突出——它显然是照着 PDP-11 量身打造的。虽然它可靠、生成的 PDP-11 代码效率更高（确实胜过 pcc），但最终成为许多系统（包括 System V 和 BSD）标准 C 编译器的，却是 pcc。

**未来难以预测**

Prentice-Hall 当初的预期是：在本书初版时已有的 130 个 UNIX 站点里，平均每个站点能卖出九本。到 1988 年 1 月，第一版已经印了超过一百万册！

pcc 随 UNIX 分发了好些年，并成为向其他许多机器移植 C 编译器时的主要蓝本。因此，不同机器上的 C 编译器表现得惊人地相似——连 pcc 的 bug 都原样传播了下去！

遇到“哪种行为才算正确”的疑问时，办法就是看 pcc 怎么处理。不幸的是，当 pcc 明显出错时，你就得面对一个难题：是要保持一致而犯错，还是要不一致而正确？

答案当然是：并没有绝对正确的做法。每种答案各有优劣。再过一阵，想做到对、或者想做到一致都不可能了，更别提两者兼得。新的 C 编译器不断涌现；当 CP/M 和 MS/DOS 上的编译器面世后，C 的人气更是暴涨。C 被移植到许多非 UNIX 环境，用在了它从未被设计来承担的各种应用上。

C 语言的定义必然会引出越来越多的分歧。库也承受着类似的压力，只是 C 应用对 UNIX 的强烈偏向让它们还算统一。然而，如今用 C 的人如此之多，需要 C 编译器的公司如此之多，一个人人可及的正经标准就成了必需。

**ANSI X3J11**

为解多个“C 语言”并存的困局，ANSI X3J11 委员会接下了定义 C 标准的任务，目标是给出一份完整、无可争辩的语言定义，以提高可移植性。这样一来，无论是写新的 C 应用还是做新的 C 编译器，都能少些猜测。

当然，以为一个标准就能解决世上所有问题，未免天真。标准有好处，也有弊端：比如，标准可能不利于使用厂商的专有扩展；标准也可能抑制采纳更新更好的设计。

X3J11 委员会的首要任务，是把今天的 C 语言原样编纂成文，只做极小的扩展。委员会采取了明智的策略：尽可能把已有的惯例和做法标准化，而不是另立新规。

委员会不会修正语言的设计错误，因为那会弄坏一大堆代码（所以别费心建议把 = 改成 :=、把 == 改成 = 了），也不会定义太多扩展，否则就没有厂商能提供合规编译器了。X3J11 只做一件事：把现存的 C 严格地定义下来，连同瑕疵一并保留。要获取标准文本或相关信息，可联系 Global Engineering Documents。

如果你想修补、改进或扩展 C，最好去看看 C++——几年之后，它无疑会经历一番 C 今天正在经历的标准化过程。

**ISO WG14**

ANSI 是美国的标准化组织。对许多非美国的公司来说，追随美国标准在政治上是不可取的，于是 ISO（国际标准化组织）也在制定一份 C 标准。它并非想标新立异，存在的意义只是让 ANSI 标准能获得许多非美国国家和公司的接受。ISO 标准纯粹是政治上的便利。

这个官方名称为 ISO TC97 SC22 WG14 的 ISO C 语言工作组，正努力确保其标准与 ANSI X3J11 完全一致。如果 ANSI 标准最终无法让 ISO 满意、导致出现两份 C 标准，那将是一场惨败。

## 3.1.2 UNIX 标准

UNIX 标准这块就没 C 标准那么顺利了。原因在于 UNIX 复杂得多，而且从未被严格定义过（见源码）。某种意义上，UNIX 的可扩展性就是它自己的阿喀琉斯之踵：既然改起来如此容易，几乎每家转售 UNIX 的公司都对它做了自己的扩展。与此同时，UNIX 要想保持吸引力，应用代码的可移植性这一理念就必须活下去。

尽管系统有千百种变体，UNIX 标准终究会成真——原因很简单：牵扯的钱太多。没有标准，就意味着大量时间和金钱浪费在移植软件上；也意味着在竞标那些指定了某个 UNIX 品牌的产品时，UNIX 厂商没法保证能报出有竞争力的标。

有意思的是，有好几个不同的机构都在制定 UNIX 标准，谁最有影响力还有待观察；其中一些标准也许会合并。（比如 AT&T 和 X/OPEN 都表示自家标准将符合 POSIX。）合并可能让标准变得更复杂，但标准这种东西，越少越好。

目前，有许多组织在尝试制定 UNIX 标准。各家目标不同，标准也就各不相同。由于 UNIX 仍在演化，这些标准没有一个试图给出完整的 UNIX 定义。因此，还有针对各子系统的、规模更小、作为补充的拟议标准（比如窗口、网络文件系统等等）。

**POSIX**

POSIX 基于 1984 年的 /usr/group 标准，由 ANSI 和 IEEE 共同制定。POSIX 的全称是 IEEE P1003 计算机环境可移植操作系统接口（Portable Operating System Interface for Computer Environments）。它用一组系统调用、库、工具和其他接口来定义类 UNIX 系统。POSIX 没有定义的东西很多，在讨论的这几个标准里，它的范围最窄。这未必是坏事：一个最小公分母，就足以在无需扩展的前提下支撑大部分 UNIX 代码。

P1003（POSIX）的组成部分：

* P1003.0 —— POSIX 指南
* P1003.1 —— 系统接口
* P1003.2 —— shell 与工具接口
* P1003.3 —— 验证与测试
* P1003.4 —— 实时
* P1003.5 —— POSIX 的 Ada 语言绑定
* P1003.6 —— 安全

美国大多数 UNIX 开发者都宣布支持 POSIX 工作，许多公司派人参与了标准化进程。

POSIX 还得到了 NBS（美国国家标准局）的支持。NBS 已经基于 1003.1 的成果发布了一份 FIPS。由于多个联邦机构催着要标准（什么标准都行），他们没有等到最终定稿。POSIX 定稿之后，NBS 的 FIPS 很可能随之修订以与之看齐。

NBS 提供了用于一致性测试的测试套件。预计政府的大多数 UNIX 系统采购都会要求兼容 POSIX，而美国政府可能会把好几笔数十亿美元的采购建立在 POSIX 标准之上。有了这种激励，厂商想必会对 POSIX 格外上心。

POSIX 还被推荐给 ISO 作为国际标准，草案建议的标准名称为 TC22 WG15。

关于 IEEE 可移植操作系统标准的更多信息，请联系 IEEE Computer Society，索取“1003.1 Posix Full Use Standard”。关于 TC22 WG15 的更多信息，参见[附录 A（地址）](../fu-lu-a-di-zhi.md)中的 TC22 WG15 条目。

**SVID**

AT&T 有自己的 UNIX 标准，名为 SVID（System V Interface Definition），又叫“紫皮书”（封面颜色）。SVID 比 POSIX 更全面，定义了更多库和命令接口。AT&T 显然不会对政府的钱视而不见，预计它会确保自家标准与 POSIX 向上兼容。AT&T 为自家标准提供一致性测试——SVVS（System V Verification Suite）就是一套测试套件，用来检验系统是否遵从 SVID。

从 System V Release 3 开始，AT&T 对自家标准采取极其严格的态度，把“UNIX System V R3”这个名称的使用与 SVID 一致性捆绑在一起：凡是自称“基于 System V R3”“兼容 System V R3”、甚至只是“含 System V R3 增强”的系统，都必须符合 SVID“基本系统”。这对想以某些方式修改系统的厂商是个麻烦——比如，加上一些伯克利增强就可能让 UNIX 不再合规。许多销售过 AT&T 早期 UNIX 修改版的厂商，如今面临两难：要么撤掉扩展（给自家客户添麻烦），要么不升级到最新的 System V。当然，也没有任何东西阻止厂商只是采纳 SVR3 的部分内容，而不宣称符合 SVR3。

SVID 的另一个缺点在于它并非厂商中立的标准。使用 AT&T 标准的公司中，AT&T 显然处于优势地位。虽说 AT&T 尚未有过朝令夕改的记录，但也没有任何机制阻止它这么做。而且，SVID 不可能不随着 System V 新版本的需要而扩充。事实上，如果是 SVID 追着 System V 跑、而不是反过来，那么其他所有 System V 兼容厂商在追求兼容的努力中，就永远比 AT&T 慢一步。由于这些原因，再加上上一段提到的那些，厂商也许会销售符合 SVID 的产品，却选择不这么宣传。

关于 AT&T SVID 的更多信息，请联系 AT&T Customer Information Center。

**X/OPEN**

迄今为止覆盖面最广的标准是 X/OPEN。它由许多欧洲公司以及美国公司（包括 AT&T）的代表共同制定，是国际标准最有希望的候选者。X/OPEN 基于 SVID，是 POSIX 的超集；它还定义了许多库、命令接口、C 语言、索引顺序访问方法（ISAM）、SQL 数据库语言，以及若干面向 UNIX 国际化使用的扩展。X/OPEN 当然也有测试套件，叫作 XVS（X/OPEN System V Specification）。

关于 X/OPEN 标准的更多信息，请联系 Elsevier Science Publishers 公司，索取《X/Open Portability Guide》。

**WeirdNIX**

P1003 委员会难得开明了一回，办了一场比赛，名为 WeirdNIX，专门征集 POSIX 标准的问题。参赛者要提交对 POSIX 标准“最丧心病狂”而又合乎条文的解释——字面上挑不出错、却违背标准本意的那种。头奖是一台 HP 计算器，外加在标准文本中留名。谁再说标准枯燥无味？
