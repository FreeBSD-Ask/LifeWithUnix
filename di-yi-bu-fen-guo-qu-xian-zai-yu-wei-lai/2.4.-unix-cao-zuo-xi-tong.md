# 2.4 UNIX：操作系统

许多人把 shell 当成 UNIX 的精髓——那是他们最先碰上、也最可能记住的部分。但程序员更可能记住这一切底下垫着的东西，也就是所谓的基础设施。

内核、系统调用与库，以及次要一些的工具（包括 shell），合起来才是 UNIX 的本体。但库和工具是后天的造物：它们可以被重写，甚至可以被无视。真正无法无视的是系统调用——那是进入 UNIX 内核的入口。如果你把它们改掉，得到的就不再是原来的操作系统，而会是另一个 UNIX 版本，或者某种与 UNIX 完全不同的东西。其余一切——每一个库子程序、每一个工具——都是照着系统调用写出来的，它们强烈地塑造了周遭一切的样貌。

那些与 UNIX 如影随形的范式，一半要归功于系统调用的设计，另一半要归功于本章别处讲到的 UNIX 哲学。

比如，程序能用同一套代码操作设备和文件（像 mv、cat、rm 等），就是因为系统调用本身就如此。打开文件“foo”读取，写的是这样的 C 代码：

```c
open("foo", READ);
```

对设备“bar”做同样的事，代码一模一样：

```c
open("bar", READ);
```

不仅基本 I/O 对设备和文件一视同仁，访问权限和命名约定也如此。这才有了 UNIX 那些概念上干干净净的工具。这个范式几乎没有例外，而且没有一个例外是人为造出来的——不像别的操作系统，打开文件和打开设备可能要用两个不同的系统调用，更别提不同种类的设备、不同访问方式的文件，等等。

内核的其他部分同样以直截了当的方式提供系统访问。比如，让程序诞生只有一个调用——execve()；权限完全由 chmod() 控制；如此等等。

当然，这种“紧致”的系统也有隐患。最大的问题是：有些东西永远套不进 UNIX 的范式。可人们还是会去套，而且分两派：一派硬塞进现有 UNIX 系统，不管多别扭（多慢）；另一派试图添加新的系统调用——彻底打碎范式的一致性（顺便把内核撑大不少）。

UNIX 最早的几个版本出自合用一间办公室的两个人，在那个环境里，讨论一处内核的增改会对别处产生什么影响是可行的。但 UNIX 一旦分发出去，这就变得困难、也基本不可能了。

一些纯粹主义狂热分子（见地下世界一章讲 Minix 的部分）认为，由研究部门发布的最后一个版本——第 7 版——才是最后的正宗 UNIX。† 这些狂热分子就像圣经原教旨主义者，听他们说话挺有趣，可在这个年代，他们的主张完全不切实际。我们没法大踏步后退——不管现代 UNIX 怎么吱呀作响，它也比 V7 能干得多。

> † 事实上，Thompson 和 Ritchie 在 V6 之后就不再把自己的名字印在手册前面了，仿佛在说他们再也无法为 UNIX 负责。

Thompson 和 Ritchie 知道自己要什么，也知道自己在干什么。他们深信 10%–90% 法则之类的东西，愿意放弃一点功能，以避开一大堆复杂度。比如，UNIX 的文件保护不提供按用户逐一检查访问的能力（不像能力表或授权表那样）；然而他们的应用几乎用不上这种细粒度的保护。

没错，他们也犯过设计错误。事实上，UNIX 的很多部分是演化的结果：不成功的东西要么拿掉（如多路复用文件），要么改掉（如文件名长度）。因为用户群小而老练，没必要永远维护旧接口。这种修改在商业操作系统里很罕见（包括近年来的 UNIX 版本）。UNIX 里错误之少，一半靠天赋式的洞察，一半靠它有机会在演化中甩掉包袱，而不必一直背着当年的错误。

自第 7 版——所有其他版本共同继承的最后一个版本——之后，人们造出许多不同的 UNIX 版本。虽然彼此有不兼容之处，几乎所有 UNIX 系统赖以立足的，仍然是那套内核调用。

内核本身并非不可触碰。AT&T 从未以任何方式保护 UNIX 内核的功能规格——这让克隆者得以在不使用任何专有源码的情况下造出自己的 UNIX 内核。有了 UNIX 标准，构建一套功能等价的系统是可能的。

内核真正要紧的，是它的接口——系统调用。你可以有一个与 AT&T 内核实现方式完全不同的内核；只要它支持那些系统调用，它就仍然是 UNIX。（这里说的不是专有的那一类，而是它的本质。）

有些工具把关于内核的知识写死在自己肚子里——这大概是 UNIX 犯下的较严重的错误之一。比如，进程状态命令 ps 会绕过所有系统调用，直接翻阅内核数据结构。写内核的时候，Thompson 和 Ritchie 的理由是：需要这类信息的程序只有一个，不值得为它新造一个系统调用；何况那些数据看起来相当依赖具体机器。

结果就是，ps 至今是个依赖机器的命令。这固然让厂商不必复刻早期 UNIX 内核的历史遗留，却也给 UNIX 的某些领域——尤其是那些需要从内核取信息的领域——带来了一点不可移植性。

厂商们试图通过扩展现有系统调用、引入新调用来弥补，这是个难题，而且因为许多 UNIX 版本的内核被完全重写，难上加难。更麻烦的是，厂商渐渐习惯了想加就加、想改就改系统调用。其结果是 UNIX 系统之间的分化。

今天的 UNIX 内核比最初的大得多。早期内核 40 KB 就装得下；现在 400 KB 的内核算小的，有些机器的内核超过 1 MB。（当然，早期内核不提供虚拟内存、网络、大的缓冲区缓存这些东西。）

随着 UNIX 内核显著增大，我们面临几个问题：大内核需要更多物理（可能还有虚拟）内存，反过来对内存管理提出苛刻要求；这类内核复杂得多，调试也难得多；它们还进一步隔绝了用户随手改造系统的可能。

许多研究者正在重新审视现代 UNIX 内核的概念，试图缩小它的体积和复杂度。比如，可以把 UNIX 内核的一部分当作用户代码重新实现——文件系统和其他设备驱动程序都有人这么干过。虽然我们通常认为这些部分需要对中断快速响应，但一个小得多的内核能跑得快得多，高响应要求的用户态代码因而可行。况且，更小的内核还能提升可靠性（代码少，错误少），也把更多控制权交给用户。
